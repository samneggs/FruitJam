Fluid FM Explained

Coloured smoke swirls across a TV while music plays, and the two react to each other. Everything you see and hear is computed live by a chip the size of a fingernail. This page explains how.

You are reading the beginner version. It assumes you are comfortable with technical ideas but not with programming. Switch level at the top at any time.

You are reading the intermediate version. It names the algorithms, data formats and program parts.

What it does

What you see and hear

Two invisible jets circle the middle of the screen. They push the fluid and release coloured smoke into it. The smoke drifts, curls into eddies and slowly fades. A row of coloured bars along the bottom of the screen shows the music's frequency spectrum, low notes on the left and high notes on the right.

The music and the smoke are linked. When a tune plays, every note shoots a small puff of smoke upward from the bars, placed left or right by its pitch. A strong bass line makes the jets push harder. In the drone mode it works the other way round: four sustained notes, one for each quarter of the screen, get louder where there is more smoke and brighter where the fluid moves faster.

With a gamepad you can steer a jet of your own, change the colour scheme, skip tunes and switch between music modes. The program also runs without a gamepad.

The program is a real-time 2D incompressible fluid simulation driving a 10-voice FM synthesizer, with the picture and the sound both sent over one HDMI cable. Two jets on a fixed orbit inject momentum and dye every frame. The dye field is colour-mapped and upscaled to the screen, with a plasma background underneath and a 64-band spectrum analyser along the bottom.

Coupling runs both ways. Fluid to sound: in drone mode each screen quadrant is sampled for mean dye (mapped to voice volume) and kinetic energy (mapped to the FM modulation index, which sets brightness). Sound to fluid: the spectrum's bass bands scale the jets' force and add a "kick" on sudden rises, the treble bands scale the dye they release, and in tune mode each MIDI note-on fires an extra jet positioned by pitch and scaled by velocity.

Hardware

The board and the chip

The board is an Adafruit Fruit Jam, built around a Raspberry Pi RP2350, a microcontroller of the kind found in small gadgets and costing a few dollars. It has two processor cores running at 246 MHz. A phone or laptop processor is many times faster and has thousands of times more memory, so the program has to be careful with both.

The chip has two kinds of memory. Inside it are 520 KB of fast memory. Next to it on the board is an 8 MB memory chip, which is roomier but slower to reach. Where each piece of data goes matters a great deal; the memory section below shows how it is split.

The chip generates the HDMI signal itself, with no graphics chip. It is programmed in MicroPython, a small version of the Python language, with the time-critical parts written as fast-running assembly code.

RP2350 on an Adafruit Fruit Jam, running the SparkFun IoT RedBoard RP2350 build of MicroPython: two Arm Cortex-M33 cores clocked at 246 MHz, each with a single-precision FPU and DSP instructions; 520 KB of on-chip SRAM; 8 MB of external PSRAM mapped into the address space through a cache. The picture leaves the chip through HSTX, a high-speed serial output that the display driver feeds with DMA, producing DVI/HDMI without any external video hardware. An optional gamepad connects over I2C.

The program is MicroPython 1.27 for control flow and setup, with every per-cell and per-sample loop written as inline Thumb-2 assembly (@micropython.asm_thumb). The assembly is generated by a Python script on a Raspberry Pi, precompiled to a .mpy module and loaded by the board, which keeps compile time and memory use on the board to a minimum.

Why a function for the main loop? MicroPython looks up module globals in a dictionary but keeps function locals in slots. The loop lives in run(), and about 120 module names are passed in as default arguments, so every name the loop touches is a fast local.

The physics

How the fluid is simulated

The screen area is divided into a grid of 160 by 120 cells. Each cell stores three numbers: how fast the fluid there moves sideways, how fast it moves up or down, and how much smoke it holds. Every frame, 62 times a second, the program updates all 19,200 cells in five steps.

  1. Stir. The jets add speed and smoke to the cells around them.
  2. Move. Everything is carried along by the flow. Each cell looks back along its own velocity to find where its new contents came from, and copies them from there.
  3. Measure. The program checks each cell for fluid piling up or thinning out. A real liquid or gas can't be squeezed like that.
  4. Balance. It works out a pressure for every cell that would undo the piling up. This takes several rounds of comparing each cell with its four neighbours, and it is the most expensive step.
  5. Correct. The pressure differences are applied to the velocities. Fluid pushed in one place now has to move aside somewhere else, which is what makes it curl into swirls.

This method is called stable fluids, published by Jos Stam in 1999 for computer graphics. Its main virtue is that it never blows up, however hard the jets push. It is not accurate enough for engineering, but it looks right, and that is the goal here.

The solver follows Stam's stable fluids scheme on a 160 × 120 collocated grid with zero velocity at the walls. Each frame:

  1. Splat. Each jet adds force and dye with a falloff over a radius of about 4 cells. The orbit positions are precomputed for all 419 steps of the orbit.
  2. Advect. Semi-Lagrangian: trace each cell centre backwards by its velocity and bilinearly sample u, v and dye at that point. Velocity decays ×0.999 per frame and dye ×0.994.
  3. Divergence. Central differences of the advected velocity.
  4. Pressure. Solve the Poisson equation with red-black successive over-relaxation (SOR, ω = 1.7). The pressure field is kept from the previous frame as a warm start, so 4 iterations are enough.
  5. Project. Subtract the pressure gradient, leaving a (nearly) divergence-free velocity field.

Number formats. Velocity, dye and the divergence scratch field are stored as 16-bit half-precision floats, which halves both the memory they take and the memory traffic of every pass. The M33 can't load half floats directly, so each kernel loads two cells as one 32-bit word and converts them in the FPU (vcvtb / vcvtt); all arithmetic is 32-bit. Pressure stays 32-bit, because the iterative solve needs the precision.

No copying. There are five field buffers: u, v, dye and two scratch fields. Each step writes into whichever buffer has just been freed, and at the end of the frame the five pointers are renamed for the next one.

The picture

From smoke to pixels

Each cell's amount of smoke is turned into a colour. The program keeps a palette of 256 colours, from black through the colours of the chosen scheme; little smoke picks a colour near the dark end, a lot of smoke a colour near the bright end. Two of the six schemes slowly rotate their hues, and each note in a tune nudges them further.

The picture in memory is 320 by 240 pixels with one byte per pixel, which allows 256 colours: 3 bits of red, 3 of green and 2 of blue. The HDMI signal is 640 by 480, so each stored pixel appears as a 2 × 2 block on the TV. The grid is coarser again: one cell covers 2 × 2 stored pixels. To avoid a blocky look, the in-between pixels are blended from neighbouring cells. A faint moving background pattern fills the areas without smoke.

Rendering is three passes, each split between the cores by screen half. First, dye is scaled and saturated to an 8-bit palette index per cell. Second, a plasma background is built from three byte-wave tables, added with saturating byte-SIMD instructions (uqadd8, four cells per operation) and kept only where it is brighter than the smoke. Third, the 160 × 120 index grid is upscaled 2× with bilinear interpolation and looked up in the palette, writing the 320 × 240 framebuffer in RGB332 (one byte per pixel). The display driver scans that out as 640 × 480 at 60 Hz.

The spectrum bars are drawn by the same upscaling pass, row by row into a small line buffer before it is copied to the screen. Drawing them in a separate pass afterwards left visible tearing lines, because the screen could be scanned out between the two writes.

The music

How the sound is made

core1 · IRQservice_flagsDriver, first in each IRQ: builds packets from queued samples and TERC4-encodes them into SRAM slots, behind the beam.
core1 · IRQseq_stepMIDI sequencer (Viper): starts and releases the notes due in the next block.
core1 · IRQfm_renderTwo-operator FM for each active voice, summed into stereo accumulators.
core1 · IRQfm_packSaturate to 16 bits and pack L|R into one word per sample.
PSRAM ringaudio_write_packed1024-sample ring, kept about 448 samples (14 ms) full.

The sound comes from FM synthesis, the technique behind 1980s instruments like the Yamaha DX7 and many game consoles of that era. Each voice is a sine wave whose pitch is wobbled very rapidly by a second sine wave. A gentle wobble gives a soft, round tone; a strong one gives a bright, buzzy tone. Changing the ratio between the two waves turns the same voice into something like a piano, a bell, an organ or a drum.

The program computes 32,000 stereo samples per second, with up to 10 notes sounding at once. Tunes come from standard MIDI files, the note-by-note format used by electronic instruments: a Bach prelude, Pachelbel's Canon, music from Holst's The Planets and an original groove written for this demo.

The sound reaches the TV over the same HDMI cable as the picture. HDMI has short gaps between the lines of the image, and real HDMI devices tuck audio into those gaps. This program does the same thing in software, packing up to four samples into each gap.

Each voice is two-operator FM: a modulator sine offsets the phase of a carrier sine. The modulation index (brightness) and amplitude glide toward their targets with one-pole smoothing, so changes never click. Everything is integer: 32-bit phase accumulators, a 1024-entry 16-bit sine table, and stereo accumulators that are saturated to 16 bits at the end.

mod = sin(modulator phase) out = sin(carrier phase + mod × index) × amplitude left += out × pan_left right += out × pan_right

Tunes are parsed on the board at start-up: tempo changes become sample times, each General MIDI instrument maps to an FM preset, and notes are assigned to voices ahead of time. Playback then only copies prepared 8-word event rows into voice state. Drums on MIDI channel 10 are FM too (kick, snare, hi-hat, crash, toms).

The audio is sent as HDMI data islands: packets placed in the horizontal blanking interval, one on every second scan line, each holding up to four stereo samples. The driver paces them against the pixel clock, so the TV receives exactly 32,000 samples per second.

Each voice is two-operator FM in integer arithmetic: 32-bit phase accumulators, a 1024-entry Q15 sine table indexed by the top 10 bits, and one-pole smoothing (x += (target − x) >> 9) on index and amplitude. Stereo is accumulated in int32 with smlabb/smlabt against Q8 pan gains, then ssat and pkhbt pack it.

m = sin[(mph += minc) >> 22] s = sin[(cph += cinc) + m · idx >> 22] v = s · a >> 15 L += v · panL R += v · panR

HDMI audio uses data islands in horizontal blanking: one island on every even line (263 per frame), up to four stereo samples each, Bresenham-paced against the pixel clock. Islands are encoded a quarter-frame at a time into 133 slots of 36 words, behind the beam. fmidi converts a standard MIDI file at load time into 8 × int32 rows (time, voice, carrier and modulator increments, index, amplitude, decay shift, note info), so the interrupt only copies rows.

After rendering, core1 runs spec: a Hann-windowed 1024-point radix-2 FFT of the ring, folded into 64 log-spaced bars from 60 Hz to 8 kHz, with bar heights taken from the float exponent bits as a cheap log2.

Two cores

Sharing the work between two cores

Every step of the simulation has to visit all 19,200 cells, so both cores work on each step at the same time. They split the work by rows of the grid. Neither core owns a fixed half. Instead, each takes the next unfinished row from a shared counter, so they finish together even if one of them is slowed down.

And core 1 does get slowed down. Besides its share of the fluid, it makes the sound: about 235 times a second it stops what it is doing for half a millisecond to compute the next batch of samples. While it is away, core 0 simply keeps taking rows. Core 0 also runs the main program, which reads the gamepad and decides what happens next.

Core 0 runs the MicroPython main loop. Core 1 is started once, installs the audio interrupt on itself, and then sits in an assembly job loop for the rest of the run. Core 0 posts a job to it (kernel address plus arguments) through a small shared array and a hardware event signal, runs its own share of the same kernel, then waits for core 1 to report it done.

For advection, divergence and projection the rows are handed out dynamically from a counter that both cores increment with exclusive load/store instructions (ldrex/strex), so no row is processed twice. This matters because the audio interrupt (about 0.5 ms, roughly every 4.25 ms) lands on core 1 at unpredictable moments; with a fixed split, core 0 used to sit idle for about 1.7 ms per frame. The counters must be in on-chip SRAM, because exclusive access is not supported on the external PSRAM. The pressure solve keeps a fixed split, because red-black ordering needs both cores to finish one colour before either starts the next; the cores meet at a barrier after each pass.

The job mailbox

A seven-word array: seq, fn, a0, a1, a2, done, a3. Core0's go1() writes a kernel's address and arguments, increments seq and executes sev. Core1 sleeps in wfe, wakes, calls the kernel with blx, issues dmb, writes done = seq and signals back. Core0 runs its own share meanwhile, then wait1() polls done.

Shared row counters

Advection, divergence and projection take rows from four int32 counters at 0x2001_FE70, reset to row 1 at the start of each frame. A claim is ldrex, add one, strex, retry on failure. The counters must be in SRAM; the RP2350's global exclusive monitor does not cover PSRAM. Cost: about a dozen cycles per row, against thousands of cycles of work per row.

The pressure barrier

Red-black SOR updates one checkerboard colour, then the other, and each colour reads the other. The grid is split at the middle row. After every colour pass each core bumps its own flag and spins until the other core's flag catches up, with a ≈1.6 s timeout so a stuck core raises an error instead of hanging the board.

Memory

Where everything is stored

Anything touched every frame goes in the chip's 520 KB of fast memory. The biggest items are the fluid itself (five grids of 19,200 two-byte numbers), the pressure grid (four-byte numbers, because the balancing step needs extra precision) and the picture. Together they fill about two thirds of the fast memory. The program code that runs every frame and the sound engine's working data are in there too.

The 8 MB memory holds what is used less often: the main program, the music, the colour palettes and lookup tables. More than half of it is still free.

MicroPython's heap spans both SRAM and PSRAM, and early allocations land in SRAM. Start-up therefore runs in two stages. The first imports the assembly kernels and the audio driver's tables, then allocates one 365 KB block and slices it by hand into the framebuffer, the pressure field, the five half-float fields and the audio packet slots. The display driver's own buffer allocations are redirected into that block while it starts. Only then does the second stage load the rest of the program, whose objects land mostly in PSRAM.

The synth block, 8,464 bytes

One SRAM allocation at 0x2001_DD70 for everything the audio interrupt and the spectrum touch. In PSRAM the interrupt took about twice as long.

Speed

Where the time goes

At 62 frames per second each frame has about 16 milliseconds. This is how they are spent, measured on the board with music playing.

Wall-clock time per frame on the board with audio playing, both cores working on each step. The audio interrupt's ≈12% of core 1 is spread across all of them.

Balancing the pressure is the largest single step, and moving the fluid along (velocity and smoke together) takes even longer. Drawing the picture is comparatively cheap. The sound engine doesn't appear in the bar because it runs in the gaps, interrupting core 1 for short bursts.

The main techniques behind these numbers: every inner loop is hand-scheduled assembly running from SRAM, using M33 instructions that MicroPython's built-in assembler does not support (emitted as raw encodings); half-float storage; rows shared between the cores; SOR with a warm start for the pressure; precomputed tables for anything that can be precomputed; and a main loop that allocates nothing, so the garbage collector never pauses it.

The loop also runs inside a function with module names bound as default arguments, because MicroPython reads locals much faster than globals. Each audio interrupt takes about 0.5 ms and produces 136 samples; just under half of that is the HDMI packet encoding and about 40% is the sequencer plus FM synthesis.

Terms

Glossary

microcontroller
A complete small computer on one chip, with processor, memory and input/output, made for embedding in devices.
core
One processor inside the chip. This chip has two, which can work at the same time.
frame
One complete picture. The demo makes 62 per second.
cell
One square of the simulation grid, holding a velocity and an amount of smoke.
pressure
Here, a number per cell used to stop fluid from piling up or thinning out.
sample
One measurement of the sound wave. 32,000 per second for each of the two stereo channels.
FM synthesis
Making a tone by rapidly varying the pitch of one sine wave with another.
MIDI file
A music file that lists notes and their timing rather than recorded sound.
FFT
A fast way to split a sound into its frequencies; it drives the spectrum bars.
interrupt
A signal that makes a core drop what it is doing, handle something urgent (here, the next batch of sound), and then carry on.
semi-Lagrangian
Advection by tracing each grid point backwards along the velocity and interpolating, which is unconditionally stable.
divergence
Net outflow from a cell; zero everywhere for an incompressible fluid.
red-black SOR
Gauss-Seidel iteration over a checkerboard ordering, overshooting each update by a factor ω (here 1.7) to converge faster. The ordering lets both cores update one colour in parallel.
float16
IEEE half-precision float: 1 sign, 5 exponent and 10 mantissa bits.
RGB332
One byte per pixel: 3 bits red, 3 green, 2 blue.
HSTX
RP2350's high-speed serial transmit peripheral, used here to produce DVI/HDMI signalling.
data island
An HDMI packet sent during blanking, used for audio samples and info frames.
ldrex / strex
Exclusive load and store: a read-modify-write that fails and retries if another core wrote in between.
SRAM / PSRAM
On-chip static RAM (fast) and external pseudo-static RAM behind a cache (large, slower).
.mpy
Precompiled MicroPython module; importing it skips parsing and compiling on the board.
asm_thumb
MicroPython's inline assembler decorator. It accepts a subset of Thumb-2; everything else (here vcvtb, vmaxnm, ldrex, uqadd8, smlabb, ssat, pkhbt, and anything using r8–r12) is emitted as data() halfwords from an encoder, each with its mnemonic as a comment.
Viper
MicroPython's native-code emitter with raw pointer types; used for the sequencer and the driver's ring-buffer routines.
vcvtb / vcvtt
Convert between float32 and the bottom or top half-word of an FPU register as float16; the only half-float support on the M33.
exclusive monitor
Hardware that makes ldrex/strex atomic. The RP2350's global monitor covers SRAM only; on PSRAM the pair is not safe between cores.
wfe / sev
Wait for event and send event: core1 sleeps in wfe until core0's sev posts a job.
dmb
Data memory barrier; core1 issues it before publishing done, so core0 never sees the flag ahead of the kernel's results.
warm start
Starting the pressure iteration from the previous frame's solution, which is already close; with SOR, four iterations suffice.
Poisson equation
∇²p = ∇·u; solving it for p and subtracting ∇p makes the velocity divergence-free.
uqadd8 / usub8 + sel
Byte-SIMD: four saturating adds in one instruction; usub8 sets per-byte flags that sel uses for a per-byte max.
TERC4
The 4-bit-to-10-bit code HDMI uses inside data islands; the driver encodes it with 256-entry lookup tables.
Bresenham pacing
Spreading 32,000 samples per second evenly over 15,780 islands per second with an integer error accumulator, as Bresenham's line algorithm does.
Q15 / Q8
Fixed-point formats with 15 or 8 fractional bits; the sine table is Q15, pan gains are Q8.
Hann window
A raised-cosine taper applied before the FFT so the block edges don't smear energy across all bars.
bit-exact bench
fluid16_bench.py runs each kernel on the board and compares every output byte with a Python reference that reproduces float32/float16 rounding.
