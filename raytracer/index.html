Raytracer in 53K
Assembly required

A Ballblazer-inspired arcade game that raytraces every pixel in real time on a microcontroller. The renderer and all of the game logic are two MicroPython @micropython.asm_thumb functions: one that never returns on core 1, and one that core 0 calls every frame. The whole game ships as one 53 KB .mpy file; 42 KB of it is machine code.

Frames from a Cortex-M33 emulator running the same machine code, shown at the 16:9 stretch the game is tuned for.

Is it really raytracing?

Yes. Every pixel casts a ray and intersects it analytically with the scene, with no polygons and no precomputed images. What it does and doesn't do:

Traced per pixel

  • Floor plane, with a box-filtered checkerboard
  • Emissive orb (sphere) and its glow
  • Three chrome defenders (ellipsoids), each with a full reflection bounce that can see the orb, the floor or the sky
  • Goal posts (cylinders) and translucent arena walls (planes)
  • A ringed gas giant: sphere plus ring plane, with the planet's shadow on the rings. It shows up in the floor and in every chrome reflection.

Shortcuts, stated plainly

  • One reflection bounce, not recursive.
  • The floor mirror intersects the primary ray with geometry mirrored through the floor. For a flat mirror that gives the same answer as tracing the reflected ray.
  • Contact shadows are an analytic soft-shadow estimate, not shadow rays.
  • Stars and sparks are projected once per frame and splatted into a light layer instead of being searched for per pixel.

Rendered at 160×120 in RGB565 and doubled to 320×240 DVI. 160×120 with 16-bit color looks better than 320×240 in 8-bit RGB332, and it leaves the per-pixel budget for reflections.

Two cores, two assembly functions

CORE 1 · rt_main · never returns
  1. Game update: steering, strafing, orb physics, defender AI, collisions, goals, spark physics
  2. Per-frame setup: camera basis, object constants, gas-giant and object row spans, light-layer splats
  3. Copies its constant table to core 0's copy and publishes the frame number
  4. Renders the even rows
  5. Waits for core 0's half, then marks the frame done
CORE 0 · Python loop + rt_rows
  1. Sees the new frame number and calls rt_rows, which renders the odd rows and returns
  2. Reads the gamepad and the palette button
  3. Waits for vsync, then 2× pixel-doubles to the DVI framebuffer (a 25-instruction asm function)
  4. Draws the HUD
sync: CTRL[SETUP] = n → core 0 renders → CTRL[HALF] = n → core 1 publishes FRAME = n. No locks: each core only writes its own counter.

What is in a frame

Rendering

  • Fresnel floor reflections of every object
  • Chrome with specular highlight, rim light and an anti-aliased equator stripe
  • Analytic edge anti-aliasing on the orb, defenders and posts, with no supersampling
  • Distance fog and a sky gradient
  • 96 fixed stars and up to 24 spark particles, splatted into byte light layers
  • Five palettes switchable live, each choosing its own scenery

Game

  • Breakaway gauntlet: carry the orb 60 tiles past three zone defenders
  • Inertia steering, strafing, straight-ahead shots
  • Defenders lead their target and ram the orb loose; touching a loose orb is a turnover
  • Sliding goal; defenders speed up after each goal
  • All of the above runs inside rt_main

How the code is built

The assembly is generated by a Python build script. It lays out a 430-entry float table and addresses it from one register with offsets of ±1020 bytes. It unrolls the per-object code, and emits one function for each core from the same row and pixel source.

MicroPython's inline assembler covers only part of Thumb-2. Everything else is emitted as data() halfwords: multiply-accumulates, vminnm/vmaxnm, saturation, pack-halfword, wide branches and negative-offset loads. 4,254 instructions are encoded that way, each with its mnemonic in a comment.

Before anything reached the board, three checks ran offline:

  • Compile: mpy-cross -march=armv7emsp compiles it, using MicroPython's real assembler.
  • Encoding: every data() line is re-assembled from its comment with GNU binutils and compared byte for byte. It flagged a push.w {lr} encoding that the ARM manual defines as UNPREDICTABLE for a single register; the 16-bit form replaced it.
  • Behaviour: both functions run in a Cortex-M33 emulator, in the same order the two cores would run them, for hundreds of frames of scripted play.

The excerpts below are shown in standard ARM (GNU) syntax. In the source, about a quarter of these lines are data() encodings; each one assembles to exactly the instruction shown.

Code highlights

Per-row object spans: skip the intersection test where it can't hit

Along one row, the discriminant of a sphere or ellipsoid test is a quadratic in the pixel index. Solving that quadratic once per row and object gives the exact pixel span that can hit, so every other pixel skips the test. Output is bit-identical with and without culling.

@ per row, per object: disc(i) = q2*i^2 + 2*q1*i + q0 is quadratic in the pixel
@ index i, so solve it once and only test pixels inside [i_lo, i_hi]
    vmul.f32 s0, s2, s2
    vmls.f32 s0, s5, s4             @ q1^2 - q2*q0
    vcmp.f32 s0, #0
    vmrs     APSR_nzcv, fpscr
    blt      IV_EMPTY1              @ this row never touches the object
    vsqrt.f32 s0, s0
    vneg.f32 s2, s2
    vadd.f32 s1, s2, s0
    vdiv.f32 s1, s1, s5             @ i_lo
    vsub.f32 s2, s2, s0
    vdiv.f32 s2, s2, s5             @ i_hi
    vmaxnm.f32 s1, s1, s3           @ clamp to the screen,
    vminnm.f32 s2, s2, s3           @ branch-free

Anti-aliasing from a miss

When a ray just misses the orb, the negative discriminant already says how far outside the silhouette it passed. One divide turns that into pixel coverage, so the edge gets blended without casting any extra rays.

@ ray vs. orb: b = oc.d, disc = b^2 - a*(|oc|^2 - r^2)
    vmls.f32 s25, s30, s19
    vcmp.f32 s25, #0
    vmrs     APSR_nzcv, fpscr
    ble      P_ORB_EDGE             @ missed -- but by how much?
    vsqrt.f32 s0, s25
    vsub.f32 s0, s24, s0
    vdiv.f32 s0, s0, s30            @ t of the hit
    ...
P_ORB_EDGE:                         @ near miss: coverage = 1 + disc * K / b
    vdiv.f32 s0, s25, s24           @ disc / b = distance outside the silhouette
    vldr     s1, [r7, #-324]        @ K = 1 / (2 r * pixel footprint)
    vmul.f32 s0, s0, s1
    vldr     s1, [r7, #-664]        @ 1.0
    vadd.f32 s0, s0, s1             @ > 0 inside the 1-pixel fringe

Arena walls without a per-pixel divide

The first version divided on every pixel. Rewriting each test as a comparison of products (A < t·B instead of A/B < t) leaves the divide only on pixels that actually show a wall or its reflection.

@ arena walls at x = +-10: t = A / B with A = distance to the wall, B = |dx|.
@ Every visibility test is a multiply; the divide only runs on wall pixels.
    vabs.f32 s1, s12                @ B
    vldr     s0, [r7, #188]         @ A (right wall)
    vcmp.f32 s12, #0
    vmrs     APSR_nzcv, fpscr
    bge      P_WPOS
    vldr     s0, [r7, #192]         @ A (left wall)
P_WPOS:
    vmul.f32 s2, s23, s1            @ nearest hit so far * B
    vcmp.f32 s0, s2                 @ A < t_hit * B  <=>  wall is in front
    vmrs     APSR_nzcv, fpscr
    bge      P_WBEHIND
    ...
P_WHIT:
    vdiv.f32 s0, s0, s1             @ only now: t

Rings with a planet shadow

The gas giant is a subroutine shared by the sky, the floor reflection and every chrome reflection. The ring test finds where the ray crosses the ring plane and looks up a 64-entry band table. It then checks whether that point is in the planet's shadow: on the night side and within one radius of the sun axis.

G_RINGS:                            @ ray vs. ring plane, then the planet's shadow on it
    vdiv.f32 s10, s3, s10           @ t to the ring plane
    ...
    vmul.f32 s14, s11, s11
    vmla.f32 s14, s12, s12
    vmla.f32 s14, s13, s13          @ |q|^2 from the planet centre
    ...
    usat     r0, #6, r0             @ (r/R)^2 -> 64-entry band table
    ...
    vcmp.f32 s8, #0                 @ ring point on the night side?
    vmrs     APSR_nzcv, fpscr
    bge      G_NOSH
    vmls.f32 s14, s8, s8            @ distance from the sun axis
    vldr     s7, [r7, #72]          @ R^2
    vcmp.f32 s14, s7
    vmrs     APSR_nzcv, fpscr
    bge      G_NOSH
    vldr     s9, [r7, #104]         @ inside the planet's shadow: 0.15

Saturating color pack

Lighting can push a channel above 1.0 (glow, specular, sparks). USAT clamps each channel to its RGB565 field width in one instruction, with no compare-and-branch.

PACK:                               @ s0, s1, s2 = linear r, g, b -> r0 = RGB565
    vldr     s6, [r7, #-412]        @ 31.99
    vmul.f32 s0, s0, s6
    vcvt.s32.f32 s0, s0
    vmov     r0, s0
    usat     r0, #5, r0             @ clamp 0..31, no branches
    vldr     s6, [r7, #-408]        @ 63.99
    vmul.f32 s1, s1, s6
    vcvt.s32.f32 s1, s1
    vmov     r1, s1
    usat     r1, #6, r1             @ clamp 0..63
    lsls     r0, r0, #11
    lsls     r1, r1, #5
    orrs     r0, r1

2× pixel doubling with pack-halfword

One 32-bit load holds two 160×120 pixels. PKHBT and PKHTB each build a word holding one pixel twice. Four stores then write the 2×2 block for both pixels: 8 bytes in, 16 bytes out, without any shifting or masking.

DCOL:
    ldr      r4, [r0]               @ two 160x120 pixels: p1:p0
    pkhbt    r5, r4, r4, lsl #16    @ p0:p0
    pkhtb    r6, r4, r4, asr #16    @ p1:p1
    str      r5, [r1]               @ row y,   pixels 0-1
    str      r6, [r1, #4]           @ row y,   pixels 2-3
    str      r5, [r7]               @ row y+1, pixels 0-1
    str      r6, [r7, #4]           @ row y+1, pixels 2-3
    adds     r0, #4
    adds     r1, #8
    adds     r7, #8
    subs     r3, #1
    bne      DCOL

How the instruction set is used

Counts are from a disassembly of the two renderer functions (plus the blit, where noted).

GroupCountHow it is used
FPU loads and stores
vldr, vstr		3,911Scene constants live in a 430-entry float table addressed from r7. With 32 single-precision registers, most constants are reloaded where needed instead of being pinned. Per-frame values (camera basis, row spans) are stored back into the table.
FPU arithmetic
vmul, vadd, vsub, vneg, vabs		2,387Ray directions, intersection terms, shading, fog.
Multiply-accumulate
vmla, vmls		785Dot products, discriminants (b² − ac) and color blends. One instruction per term and no temporary register.
Compare and flag transfer
vcmp, vcmpe, vmrs		842Every decision on a float is a pair: the compare sets the FPU flags, vmrs copies them to the core so a branch can test them.
Conversions and moves
vcvt, vmov		393Float to integer for color channels, table indices and texel lookups.
Divide and square root
vdiv, vsqrt		331About 14 cycles each, so much of the design is about avoiding them: one divide per floor row, object spans solved once per row, wall tests rewritten as products.
Min and max
vminnm, vmaxnm		140Branch-free clamps for fog, edge coverage and spans. These are new in the Armv8-M FPU (FPv5) and not available on a Cortex-M4.
Integer constants
movw, movt, movs		67932-bit addresses and bit patterns: the control block, light layers, texture tables.
Branches
b<cc>, b, bl		705Per-pixel dispatch (sky, floor, object, wall), loop control and subroutine calls. Once the functions outgrew the short branch range, the build switched to the 32-bit forms.
Saturation and packing
usat, pkhbt, pkhtb		22 + 2usat clamps color channels to their 5- and 6-bit fields and clamps table indices. pkhbt/pkhtb do the pixel doubling in the separate blit function. The pack-halfword instructions come from the Armv7E-M DSP extension; its packed-integer SIMD instructions suit fixed-point audio and image filters and have little use in a float renderer.

The rest is ordinary integer work: loads and stores to the control block and light layers, address arithmetic, and the game-logic bookkeeping. Overall, 78% of the instructions run on the FPU.
